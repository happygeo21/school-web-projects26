## 2. permission_denied의 근거와 한계

사용자가 제공한 Rules 화면에서 `/memoryTemperature2026/submissions/{schoolId}/{uid}/{entryId}`의 학생 본인 쓰기 및 교사 이메일 기반 읽기 조건을 확인했습니다. **학생 자신의 자료 읽기는 허용되지 않은 화면이므로 저장 전 get()를 요구하면 정상 쓰기까지 막을 수 있습니다.** 현재 학생 제출은 선행 DB 읽기를 요구하지 않습니다.

초기 증상 원인은 단정하지 않습니다. 익명 제공자 활성화/토큰 만료/승인 도메인/UID 불일치와, DB 경로 권한·필수 필드·좌표·점수 검증 거부는 별도 점검해야 합니다. RTDB는 검증 실패에도 permission_denied를 반환할 수 있습니다. 현재 Rules 전체 원문과 게시 시점, 실제 익명 로그인 상태가 없어 운영 원인 확정은 남았습니다.

새 후보 Rules는 학생 본인 생성·동일 payload 재시도만 허용하고, 다른 학생 읽기/수정·공개 승인·원인지도 변경·원본 물리 삭제를 거부하도록 설계했습니다. 이 규칙은 운영에 게시하지 않았습니다. 로컬 Emulator는 차단됐지만 CI #1에서 claim 기반 규칙 테스트가 성공했습니다. 기존 Rules에 있는 학생 임의 덮어쓰기 권한까지 클라이언트만으로 제거할 수는 없습니다.

현재 Google/이메일 로그인과 `TEACHER_AUTH_MODE='existing-rules'`는 유지합니다. 별도 claim 방식을 무단 도입하지 않습니다. [RULES-MIGRATION.md](RULES-MIGRATION.md)에 현재 이메일 승인식을 보존하는 **오프라인 검토용 병합 절차**, claim 이행 선택지, 다른 앱 루트 보존, 원본 백업·복구를 설명했습니다. 후보 JSON 전체를 운영 DB에 붙여넣으면 다른 앱이 차단될 수 있습니다.

### B. 실제 Chromium + Firebase SDK 대역

브라우저 통합 **1/1 통과**. 하나의 통합 테스트 안에서 다음을 실행했습니다. 운영 Firebase 요청은 모두 차단하고 가상 데이터만 사용합니다.

- 학생 3단계·7학교 각각 제출, 익명 UID 경로/학교 일치
- S1 권한 거부 → 내용 보존 → 새로고침 → 인지도/초안/최초 payload 복원 → 위치 재확인 → 동일 ID 재시도
- 나머지 학교의 토큰 갱신 실패 안내 → 저장 요청 0건 → 갱신 후 제출
- 계정 변경 시 제출 비활성화, 초안 지우기 후 재로딩 때 재생성 방지
- 빈 공식 캐시 안내·수동 위치, 별도 검증용 가상 캐시의 자동완성 선택·이름/주소/좌표/공식 상태
- 직접 업로드 기본 비활성화 상태의 텍스트·외부 링크 독립 제출; 파일 업로드는 SDK 대역에서만 별도 스위치로 검사
- 교사 수정 요청의 audit·revision·공개 해제, 원인지도 비수정, 이력 XSS 방어, 보관 요청
- 새 공개 요청의 opaque 키, 활동코드·UID·탐구 entryId 제외, 작품 승인 상태·공개 사본 atomic 요청

이는 실제 브라우저에서 SDK **대역**으로 실행한 결과입니다. Firebase Auth 서비스·서버 권한·실제 외부 링크 응답을 검증한 결과로 해석하면 안 됩니다. 서버 규칙 후보는 아래 C의 CI 결과와 구분하며, 실제 운영 계정/게시본에 대한 검증은 D가 남아 있습니다.

### C. Firebase Emulator

테스트 **6개 시나리오, 로컬 0개 실행**. Node 24.19.0·Java 21·Firebase CLI 14.22.0 확인 후 재실행했으나 `firebase-database-emulator-v4.11.2.jar` 다운로드에서 **403 Domain forbidden**으로 종료했습니다. 증거: 현재 머신 `/tmp/veteransgeo-phase2-emulator.log`. 인증정보/검증 끄기/검증되지 않은 바이너리로 우회하지 않았습니다.

대안으로 `.github/workflows/veteransgeo-review.yml`을 추가했고, [CI #1](https://github.com/happygeo21/school-web-projects26/actions/runs/40806967095)의 **Success**를 GitHub 요약 화면에서 확인했습니다 (검증 코드 커밋 `1fd65044483c8b54aef77373b214d2741e76e2e2`, 소요 2분 1초). 해당 workflow에는 claim 기반 Emulator 테스트 6개를 실행하는 npm test가 포함됩니다. 상세 stdout 로그는 GitHub 로그인이 필요해 이 세션에서 읽지 못했습니다.

추가로 기존 이메일 승인식을 보존한 병합본에도 같은 6개 시나리오를 적용하도록 보완했습니다. 이 추가 검사의 결과는 다음 CI 결과로 별도 확인해야 합니다. 이 브랜치 push/PR에서 Node22·Java21·데모 프로젝트 `demo-veteransgeo`만 사용하며 contents:read 권한이고 배포 단계·운영 비밀키가 없습니다. **workflow 파일 존재·push 성공은 실행 성공을 뜻하지 않습니다.** 최종 보고에서 확인된 실행 결과만 기재합니다. 로컬 네트워크에 storage.googleapis.com 허용이 적용되면 같은 명령으로 재개할 수 있습니다.

## 5. 공식 데이터 갱신 도구

[갱신 절차·입력 명세](FACILITY-IMPORT.md). 공식 안내/HTTPS JSON endpoint에 다시 요청했으나 프록시 403입니다. 실제 데이터를 생성하지 않았습니다. 도구는 원문·검토 JSON을 저장소 밖에서 받아 새 검토용 캐시만 생성하고, 공식 좌표계가 EPSG:4326이 아니면 변환을 추정하지 않습니다. 라이선스·응답/인증/CORS 검토·원문 SHA256·독립 지도 대조가 필요합니다.

공식 실데이터가 연결되기 전에는 공식지도 외부 확인·일반 지도 검색·수동 핀·좌표 붙여넣기를 사용합니다. 일반 검색 결과와 직접 제안 장소를 공식 지정 시설로 표시하지 마세요. 이미 공식자료를 본 후에는 사전 측정으로 위장해 원자료를 바꾸지 않습니다.

## 6. 사람이 해야 할 Console 설정·비용

Spark 무료 요금제와 Storage 업그레이드 요구 화면은 사용자 제공 자료로 확인했습니다. 요금제·결제·Rules는 바꾸지 않았습니다. 텍스트/링크는 Storage를 사용하지 않지만 RTDB 무료 할당량 내에서 운영해야 합니다.

1. 실제 게시된 전체 RTDB Rules를 비공개 백업하고 이 도구로 비교/검토용 병합합니다. Emulator와 테스트 프로젝트 실측 후 별도 게시 승인이 필요합니다.
2. 익명·Google·이메일 제공자 활성화 및 실제 Pages/Netlify 승인 도메인을 확인합니다. 기존 교사 승인 목록·계정은 유지합니다. 이메일 인증 여부와 claim 이행은 계정 누락 없이 별도 검토합니다.
3. 신규 works/publishedWorks/audit/workAudit 경로 권한이 없으면 텍스트·링크 제출/검토도 운영 저장되지 않습니다. UI 구현 완료와 운영 사용 가능을 구별하세요.
4. 파일 직접 업로드는 추가 요금제·버킷·Rules·CORS·다운로드 토큰·미승인 접근을 검증하기 전까지 false입니다. 파일 저장/전송/요청·서버 검사·API 중계에는 비용이 발생할 수 있습니다. 무료 단계에서 Blaze를 요구하지 않습니다.
5. 외부에 공개된 Drive/YouTube 원본은 앱 승인과 별도로 접근 가능할 수 있습니다. 앱에서 비공개로 바꿔도 외부 원본 권한·다운로드 사본을 회수하지 못합니다. 교사가 실제 링크를 새 창에서 확인해야 합니다. 미리보기는 이용자가 버튼을 눌러야 외부 서비스를 로드합니다.

## 7. 수업 적용 가능 범위와 남은 결함

**현재 가능한 범위:** 로컬/검토 환경에서 3단계 탐구, 공식지도 참고·수동 위치, 초안 복원, 가상 계정으로 교사 수정·작품 흐름·CSV 검토. 기존 운영판을 이 브랜치로 자동 교체하지 않았습니다.

**아직 바로 운영 수업에 쓸 수 없는 범위:** 미검증 신규 Rules가 필요한 저장/교사 수정/작품 승인, 실제 공식시설 자동목록, 실제 파일 업로드. 네트워크 허용 초안 저장만으로 현재 머신 접근이 가능해지지 않았습니다.

추가 한계:

- 탭 종료·2시간 만료·브라우저 보관 차단·기기 변경 후 복원은 보장하지 않습니다. 공용 기기는 초안 지우기를 사용하세요.
- 새 공개 사본에는 private 식별자를 넣지 않지만, 기존 운영 `published` 복합키에 UID가 이미 있을 수 있습니다. 운영 데이터를 건드리지 않았으므로 완전한 과거 키 비식별화는 별도 승인 이관이 필요합니다. 자유서술의 개인정보/저작권은 교사 검토가 필요합니다.
- 교사 UI는 수정/보관과 audit를 원자적으로 요청합니다. 서버 규칙만으로 승인된 교사의 직접 클라이언트 수정에 audit를 반드시 동반하도록 강제하는 별도 백엔드까지 구현하지는 않았습니다.
- claim 후보의 stale revision 거부는 CI #1에서 검증했습니다. 복원·공개 중단의 실제 사용자 동시성은 운영 테스트가 남았습니다. 실제 링크 접근권한/삭제 상태는 CORS·로그인 때문에 앱이 자동 확정하지 않습니다.
- MIME/서명 검사는 악성파일 검사·EXIF 제거·저작권 검증을 대체하지 않습니다. 미래 파일 운영에는 서버 검사·할당량·비용 통제가 추가로 필요합니다.
