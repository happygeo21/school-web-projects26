## 6. 별도 승인 후에만 할 배포 순서

**중요: 무중단 Rules-first 전환은 현재 후보로 보장되지 않습니다.** 새 Rules는 신규 자료에 awarenessOriginal을 요구하지만 이전 학생 웹 코드는 이를 보내지 않습니다. 새 웹을 먼저 올리면 works/audit 경로가 기존 Rules에서 거부될 수 있습니다. 이전 교사 화면은 새 공개 키/보관 정책도 모르므로, 한쪽만 장시간 운영하지 않습니다.

1. 위 리허설·원본 백업·두 사이트 설정 확인을 마친 뒤, main 병합/Rules 게시/Pages·Netlify 배포 범위에 대해 **별도 승인**을 받습니다. 지금은 이 선을 넘지 않습니다.
2. 수업 외 점검 시간을 잡고 양쪽 사이트의 작성/제출·교사 승인 작업을 멈춥니다. 진행 중 내용을 제출/별도 보관하게 하며 브라우저 저장소를 무조건 삭제하지 않습니다. 기존 탭 재사용을 막고 새로고침 안내를 준비합니다.
3. 이전 Pages 커밋·Netlify Published 배포 ID·현재 전체 Rules 원본 해시를 확보합니다. 다른 앱 루트와 글로벌 권한이 유지되는지 마지막으로 비교합니다.
4. 점검 중 검증된 **현재 이메일 승인식 병합본**을 게시하고, 승인된 코드만 main에 병합하여 Pages 자동 배포와 해당 Netlify 배포를 완료합니다. 이 순서는 점검 시간에만 사용합니다. 한쪽 실패 시 수업을 재개하지 않습니다.
5. 기존 주소에서 각각 확인합니다: Pages `/school-web-projects26/veteransgeo/index.html`, `teacher.html`, `public.html`; Netlify 기존 호스트의 `/`, `/teacher.html`, `/public.html`. 폴더/파일 이름·도메인은 바꾸지 않습니다. `security/REVIEW.md`, Rules, package 파일은 404여야 합니다. API 점검 도구도 공개 산출물에 넣지 않습니다.
6. 운영에 테스트 레코드를 쓰지 않는 이번 범위를 유지하려면, 테스트 프로젝트 실측 + 운영의 비파괴 인증/권한·파일 응답 점검까지만 확인합니다. 운영 제출 쓰기 smoke test가 별도로 필요하면 그 범위도 별도 승인받아야 합니다. 링크/정적 페이지 성공만으로 운영 저장 성공을 보장하지 않습니다.
7. 두 사이트/교사 승인 계정/공개 범위를 확인한 뒤 점검 해제합니다. MEDIA_UPLOAD_ENABLED=false와 Spark를 유지합니다.

Pages는 공통 _site를 배포하므로 다른 앱 파일도 같은 산출물에 포함됩니다. 다른 앱 소스는 변경하지 않았으나 실제 Netlify 연결 사이트의 main-trigger 영향은 Console에서 별도로 확인해야 합니다. 운영 주소 유지의 코드 검토와 실제 배포 확인을 구분합니다.

## 7. 복구 계획

- 준비 단계 실패: 운영 변경 없음. 후보·CI·비공개 백업을 보존하고 적용을 중단합니다.
- 전환 중 한쪽 실패: 점검 유지 → 이전 Pages 코드와 해당 Netlify Published 버전 복구 → Rules의 기억의 좌표 루트를 백업 기준으로 복구하는 검토 수행 → 두 사이트와 기존 승인 계정 확인 후 재개합니다. **새 Rules에 이전 웹만 복구하면 제출이 계속 거부될 수 있습니다.**
- 그동안 다른 앱 Rules가 바뀌었다면 과거 전체 파일을 통째로 게시하지 않습니다. 최신 다른 루트·전역 권한을 보존한 상태에서 해당 앱 루트 복구 후보만 만들고 검증합니다.
- 학생 원본·새 이력·보관 상태를 삭제/리셋하지 않습니다. 이전 교사 UI는 deletedAt 보관 상태를 모를 수 있어 롤백 기간의 수정/승인은 중지하고 자료를 확인해야 합니다.
- 코드 취소는 3차 변경 또는 필요한 2차 커밋을 최신순 revert하는 **별도 검토 브랜치/PR**로 진행합니다. main reset/force push는 하지 않습니다.

## 8. 현재 남은 입력과 완료 판정

필요 입력: (1) 현재 게시된 전체 Rules의 비공개 원문, (2) 실제 Netlify 운영 주소·base/publish/배포 ID, (3) 별도 테스트 프로젝트 및 가상 계정 리허설 결과, (4) 공식 점검 CI의 로그인 후 Summary 또는 승인된 네트워크에서 얻은 공식 명세/응답.

이 자료가 없는 상태에서 실제 병합본 검증·운영 주소 검증·실제 Auth 성공을 완료로 표시하지 않습니다. 공식 캐시는 빈 상태를 유지하고 수동 입력을 사용합니다. PR은 Draft이며 main 병합/Rules 게시/배포는 승인이 있어도 이번 작업 범위에서 자동 실행하지 않습니다.
