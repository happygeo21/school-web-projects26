- 로컬 28개 검사 통과: 기존 명령 11 + 신규 업무 등록 14 + 웹훅 등록 도우미 3. Notion/Telegram HTTP는 모의 응답이고, SQL은 실제 SQLite에 실제 마이그레이션을 적용하여 실행했다. Cloudflare D1/Worker 통합 검증은 별도다.
- `/request`, `/requests`는 1순위 실연동 확인 후 진행. 공개 Issue 작성, 원격 AI 실행, 새 정기 알림은 추가하지 않았다.

## 교사용 사용법

```text
/add 통합사회 활동지 준비 | 내일
/add eGIS 학생 안내문 점검 | 2026-11-06
업무등록 통합사회 활동지 준비 | 모레
```

기한은 Asia/Seoul 기준 `오늘`, `내일`, `모레`, `YYYY-MM-DD`만 지원한다. 날짜만 저장하며 마감 시각을 임의로 만들지 않는다. 지난 날짜·잘못된 날짜·빈 제목은 거절한다.

저장 위치·제목·기한을 보여주는 인라인 버튼에서 **등록 승인**을 눌러야 저장한다. **취소** 또는 10분 경과 시 저장하지 않는다. 저장 성공은 새 페이지 ID, 부모 업무함, 제목·기한·기본값·원본 식별키와 링크를 GET으로 재조회한 뒤 알린다.

제목은 2~160자로 제한한다. 학생 개인 정보, 숫자, 이메일, 전화번호, 일부 이름 패턴과 인증키 패턴은 확인 화면·D1·Notion에 보내기 전에 거절한다. 이름 판별은 완전하지 않으며 일반 단어도 보수적으로 차단할 수 있다. 개인 정보가 없는 일반 업무명만 입력하고 승인 전 직접 확인한다. 이미 Telegram에 입력한 원문 자체를 봇이 수신하지 않게 할 수는 없다. 거절한 원문은 회신하지 않으며 로그에 기록하지 않는다.

## 실제 확인한 업무함 스키마

대상 data source: `16c3caf5-6bc2-4758-aeae-7b9ba855b2a7`.

| 속성 | 실제 유형 | 신규 값 |
|---|---|---|
| 업무명 | title | 승인한 업무명 |
| 마감일시 | date | YYYY-MM-DD |
| 정보 등급 | select | 일반 업무 |
| 진행 상태 | status | 수집됨 (실제 미완료 기본값) |
| 교사 완료 확인 | checkbox | false |
| 원본 식별키 | rich_text | telegram:승인ID |

`업무 ID`는 Notion 자동 증가 속성이므로 쓰지 않는다. Notion API가 요구하는 title을 제공하며, 추가 업무 분류 등 선택 속성은 임의로 채우지 않는다. 실행 때에도 GET으로 정확한 속성 유형과 선택지 ID를 확인하며, 선택지를 새로 만들지 않는다. 확인 화면 이후 속성·선택지 ID가 달라지면 저장을 중단한다. 별도 연결의 Insert content 권한은 실제 승인 테스트 전에는 확정할 수 없다.

## D1을 선택한 이유와 실패 처리

| 선택 | 중복 클릭 처리 | 판단 |
|---|---|---|
| KV | eventual consistency, 원자적 상태 전환 없음 | 승인 잠금에 사용하지 않음 |
| D1 | UNIQUE 이벤트 번호, 조건부 UPDATE … RETURNING | 선택 |

개인용 비공개 D1 하나와 `migrations/0001_task_approvals.sql`을 사용한다. 세션은 `first-primary`로 시작하여 같은 요청 안의 읽기·쓰기 순서를 보장한다. 어떤 유료 플랜도 자동 활성화하지 않는다. 현재 요금제의 Workers·D1 Free 한도를 소유자가 확인하고 한도 초과 시 처리를 멈춘다. 개발·빌드에 유료 AI API는 필요 없다.

- Telegram `update_id` UNIQUE로 명령 재전송을 같은 승인 항목으로 묶는다. 승인 버튼은 무작위 ID만 담는다.
- `pending → creating` 조건부 갱신에 성공한 한 요청만 `POST /pages`를 한 번 호출한다. 다른 요청은 새 업무를 만들지 않는다.
- 생성 응답 유실·Worker 중단·Notion 오류(401/403/429 포함) 후에는 자동 재생성하지 않는다. 동일 버튼으로 식별키 검색 → 페이지 GET만 수행한다.
- API가 실제로 저장하지 않은 실패도 안전을 위해 잠긴다. Notion 검색에서 결과가 안 보여도 지연일 수 있으므로 기존 상태를 pending으로 되돌리거나 새 `/add`로 다시 등록하지 않는다. 소유자가 원본과 실행 상태를 확인할 때까지 보류한다. 외부 API와 D1 사이에 단일 트랜잭션이 없기 때문에 자동 재시도와 무조건적 exactly-once 완료를 동시에 보장하지 않는다.
- 취소·만료·성공 항목의 제목·기한·스키마는 지운다. 만료 항목 정리는 다음 `/add` 또는 버튼 입력 시 수행되며 정기 알림은 추가하지 않는다. 승인 유효기간은 활동 여부와 관계없이 적용된다.
- `creating`의 최소 업무명·기한·식별키는 불확실한 저장을 검증하기 위해 유지한다. 이 상태의 자료 정리는 소유자 확인 후 별도로 처리하며 기존 Notion 항목은 수정하지 않는다.
- ID·이벤트 번호·상태와 성공 페이지 링크는 오래된 웹훅 재전송 방지를 위해 보관한다. D1을 삭제·초기화하거나 이전 백업으로 복구하면 중복 방지 근거가 사라질 수 있으므로 원복 시에도 보존한다.
- Telegram 응답 메시지 자체는 재전송될 수 있다. 그 경우 Notion 생성은 반복하지 않는다.

## 배포 전 읽기 전용 비교 — 반드시 먼저

1. Cloudflare에서 **현재 트래픽을 받는 버전/배포 ID**를 확인한다. 최신 업로드 버전은 활성 버전과 다를 수 있고, 여러 버전이 트래픽을 나누면 각 활성 버전을 모두 확인한다. 이어서 소스 전체 모듈, compatibility date, 라우트, D1 등 바인딩 이름, 시크릿 이름만 확인한다. 토큰 값은 열거나 출력하지 않는다.
2. 현재 버전 소스를 비공개 위치에 보관하고 최신 main의 `src/index.js`와 비교한다. 대시보드 직접 수정이 있는지 확인한다. 소스의 해시가 다르면 비밀값을 제거한 코드 차이를 검토하고 필요한 운영 수정을 브랜치에 반영한다. `/health=ok`만으로 소스가 같다고 판정하지 않는다.
3. 기준 버전 ID와 코드 해시, 차이 검토 결과, 기존 바인딩 이름, 원복할 버전을 비공개 기록에 남긴다. 실제 데이터와 비밀값은 공개 PR에 올리지 않는다.
4. **비교 완료 전 운영 Worker를 배포하지 않는다.** 비교 완료 후 테스트 결과·최종 PR 차이와 함께 사용자에게 배포 승인을 받는다. 이 문서에는 배포 자동 실행 기능이 없다.

## 권한 준비

기존 봇 계정/토큰, 기존 읽기 연결 `NOTION_API_TOKEN`, GitHub Secrets와 알림 자동화는 그대로 유지한다.

1. 별도 Notion 내부 연결을 만든다. **Read content + Insert content만**, Update content·댓글·사용자 정보는 허용하지 않는다. 기존 업무함 원본 데이터베이스 하나에만 연결한다. 하위 페이지 상속 범위도 확인한다. 상위 작업공간이나 학생 자료를 공유하지 않는다.
2. 배포 승인 전에는 `wrangler versions secret put NOTION_WRITE_TOKEN --name geoteacher-telegram-gateway`의 비표시 입력창으로 **미배포 버전**에만 저장한다. `wrangler secret put`은 즉시 배포하므로 이 단계에서 실행하지 않는다. 대시보드의 Deploy/Save and deploy도 누르지 않는다. Secret 추가 후 활성 배포 ID와 트래픽 버전이 그대로인지 확인한다. 읽기 토큰과 같으면 등록 기능을 차단한다. 값은 채팅·GitHub·로그·명령행 인자에 붙이지 않는다. [Secret 공식 문서](https://developers.cloudflare.com/workers/configuration/secrets/) 참고.
3. 기존 `TELEGRAM_CHAT_ID`와 sender ID를 모두 검사한다. 별도 `TELEGRAM_SENDER_ID`가 없으면 개인 채팅 ID와 같은 사용자만 허용한다. 웹훅 Secret 인증도 유지한다.
4. 비공개 D1을 Free 한도 안에서 준비하고 `TASK_DB`를 **배포 후보 설정에** 추가한다. 운영 Worker의 바인딩 활성화는 배포 승인 뒤에만 한다. 마이그레이션은 이 새 DB에만 적용한다. Firebase/학생 데이터/기존 Notion 업무를 이 DB로 복사하지 않는다.

## 승인 후 배포 순서

운영 소스 비교·백업과 사용자 승인이 선행 조건이다. 아래 명령은 권한 있는 소유자 환경에서만 실행하며 이 PR 작성 중에는 실행하지 않았다.

1. 검토한 PR 커밋을 checkout하고 `npm test`를 실행한다(Node 22.13+와 Python 3.12+, 외부 라이브러리 불필요).
2. 기존 Worker의 모든 기존 바인딩·일반 설정을 반영한 비공개 Wrangler 설정을 준비한다. 저장소 `wrangler.toml`의 예시를 그대로 덮어쓰지 않는다. 특히 기존 Secret을 제거하거나 기존 봇 토큰을 바꾸지 않는다.
3. `[[d1_databases]]`의 `binding="TASK_DB"`, 실제 DB ID와 `migrations_dir="migrations"`를 설정한다. 새 D1 생성 또는 원격 마이그레이션 적용도 승인한 대상에서만 한다. `wrangler d1 migrations apply geoteacher-task-approvals --remote` 후 테이블을 확인한다. 유료 플랜 가입은 실행하지 않는다.
4. 최초에는 `ADD_ENABLED="false"`로 두 모듈(`src/index.js`, `src/task-add.js`)을 함께 배포한다. Wrangler 번들 또는 두 모듈을 지원하는 대시보드 편집기를 사용한다. Worker의 이름·라우트·기존 설정을 재확인한다.
5. `/health`, 기존 `/ping`, `/today`, `/status`, `/projects`, `/aside`가 유지되는지 확인한다. **이 시점에 Notion 신규 저장은 차단되어야 한다.**
6. 준비된 Secret·D1·스키마를 확인한 뒤 `ADD_ENABLED="true"`로 활성화한다.
7. 기존 GitHub `GeoTeacher Telegram Webhook Setup`의 `install`을 승인 범위 안에서 재실행하여 `allowed_updates=["message","callback_query"]`로 바꾼다. URL·토큰·secret·단일 수신기는 유지한다. 새 도우미는 대기 메시지를 버리지 않는다(`drop_pending_updates=false`). `getUpdates`/pair는 실행하지 않는다. PR 미병합 상태라면 main의 이전 도우미는 callback을 구독하지 않고 대기 메시지를 버린다. 반드시 검토한 PR 브랜치를 선택하거나 해당 변경을 병합한 뒤 실행한다.
8. 아래 1건 실저장 테스트를 완료하고, 실패하면 즉시 비활성화/원복한다. 이 확인 전에는 기능을 운영 완료로 보고하지 않는다.

## 사용자 승인 후 실제 저장 테스트 — 비민감 업무 1건만

승인받을 테스트 제목: **GeoTeacher 업무 등록 연결 점검**, 기한: **테스트 당일(Asia/Seoul)**.

- 운영 봇에서 `/add GeoTeacher 업무 등록 연결 점검 | 오늘`을 보내고, 표시된 위치·날짜와 개인정보 없는 제목을 확인한다.
- 승인 전: D1 pending과 해당 식별키의 Notion 검색 0건을 읽기 전용으로 확인한다.
- 인라인 **등록 승인**을 한 번 누른다. Telegram 성공 응답의 ID·링크와 같은 페이지를 Notion에서 재조회하여 실제 속성을 확인한다.
- 같은 버튼 재클릭/동일 웹훅 재전송 후 식별키로 검색한 페이지가 정확히 1건인지 확인한다. 새 `/add`로 두 번째 테스트 업무를 만들지 않는다.
- 취소·만료·거절·오류 시나리오는 로컬 모의 테스트로 검증한다. 추가 실제 저장 테스트 업무를 임의로 만들지 않는다.
- 생성된 테스트 항목도 임의 삭제하거나 완료 처리하지 않는다. 테스트 ID·원본 링크·확인시각을 비공개 운영 기록에 남긴다. 제목이나 원본 업무 내용은 공개 로그에 복사하지 않는다.

## 즉시 원복

등록 오류가 발생하면 먼저 `ADD_ENABLED=false`로 새 저장을 막는다. 이미 `creating`인 항목이 있으면 D1과 Notion 식별키를 보존하고 실행 중 요청이 종료됐는지 확인한다. Cloudflare Deployments에서 사전에 기록한 이전 정상 Worker 버전으로 되돌린다. D1·봇 토큰·읽기 연결·기존 Notion 항목은 삭제하지 않는다. 이후 `/health`, `/ping`, `/today`, `/status`, 기존 GitHub 알림 설정을 확인한다. 웹훅 URL은 Cloudflare 하나를 유지하며, 필요한 경우에만 `allowed_updates=["message"]`로 복구한다. 기존 알림이나 Notion 아침 브리핑을 새로 발송하지 않는다.
