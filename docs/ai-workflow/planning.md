# 기획·밑그림·방향 제안

## 사용자가 갈피를 못 잡을 때

- 현재 목표를 사용자 말로 한 문장으로 정리한다. 문제를 목적 미정 / 대상 미정 / 정보 구조 / 디자인 / 기능·데이터 / 도구 선택 / 배포 중 어디에 있는지 구분한다.
- 이미 알려진 조건을 활용하고, 결과를 크게 바꾸는 질문만 1~3개 묻는다. 선택지를 제시할 수 있으면 자유서술 부담을 줄인다.
- 현실적인 2~3안을 비교한다: 적합한 사용자·장점·포기할 점·구현 및 유지 부담. 가장 적합한 1안과 이유, 지금 할 다음 행동을 함께 제안한다.
- 예: “학생이 수업 중 빨리 제출하는 것이 목적이므로 첫 버전은 시작→입력→완료만 만들고 교사 결과 화면을 더하는 안을 추천합니다.”
- 모순되는 요구나 과도한 기능이 보이면 그대로 늘리지 말고 수업 목적과의 충돌을 설명한다. 필수 / 나중 / 제외를 정리하고 완료 기준을 고정한다.
- 세부 구현은 자율적으로 진행하고 디자인 방향·사용자 정보 수집 등 큰 결정은 사용자 선택이나 기존 위임을 따른다. 대안을 반복 제안하며 이미 확정한 안을 흔들지 않는다.

## 시작할 때 기록할 것

목적, 사용자, 기기, 핵심 행동, 필요한 화면, 데이터의 저장 여부, 완료 기준, 기존 기능 보존 범위. 디자인에는 색의 역할과 정확한 값, 한글 글꼴, 본문 크기, 말투를 더한다. 짧은 수정은 대화 안에 정리하고 큰 작업은 대상 폴더의 기획 문서로 남긴다.

## 먼저 그릴 작업과 바로 고칠 작업

- 신규 앱·구조 변경·여러 화면 연결·반복적인 디자인 재작업에는 밑그림을 만든다.
- 오탈자·한 버튼의 동작·재현된 오류·이미 정해진 디자인의 작은 변경은 바로 수정한다.
- 코드 제작 전 종이 스케치, 간단한 HTML 와이어프레임, 도구에서 받은 시안 등 가장 저렴한 수단을 선택한다. Stitch를 반드시 거칠 필요는 없다.
- 시안 시간까지 포함해 판단한다. 확인하지 않은 토큰 절감률이나 생산성 수치를 약속하지 않는다.

## 화면을 잇고 확정하기

1. 첫 화면의 정보 구조와 주 행동을 고른다. 글자만 바꾸는 요청을 전체 화면 재생성으로 처리하지 않는다.
2. 시작→입력→완료→결과 등 실제 이동 경로를 적고 뒤로 가기·취소·실패·재시도 경로도 정의한다.
3. 필요한 화면만 추가한다. 설정·알림·로그인은 목적에 필요할 때만 넣는다.
4. 화면을 나란히 비교해 제목 위치, 버튼 크기, 여백, 표현을 맞춘다.
5. 선택된 시안을 고정하고 다음 화면은 같은 규칙을 따른다. 국소 수정은 지정된 요소만 바꾼다.

## 규칙과 인수인계

확정 후 대상 프로젝트의 DESIGN.md에 반복되는 색·한글 글꼴·크기·간격·모서리·그림자·버튼 상태·금지 사항을 적는다. 우연히 한 화면에만 등장한 장식을 전체 규칙으로 승격하지 않는다.

구현 기준으로 화면 시안, DESIGN.md, 화면 전환 설명을 함께 사용한다. 자료가 부족하면 큰 차이를 만드는 누락만 확인한다. 시안과 구현의 차이는 구체적으로 보고하며 화면 내보내기 코드를 그대로 운영 코드로 간주하지 않는다.

## 화면과 백엔드의 경계

화면 이동이 된다는 사실과 저장·인증·권한·중복 제출 방지가 동작한다는 사실을 구분한다. 실제 서비스가 필요하면 저장 구조와 접근 권한을 따로 설계한다. 코드 복구와 데이터 복구는 별개다.

학생 정보는 시안 단계부터 최소화하고 테스트에는 가상 자료만 쓴다. 익명이라고 쓰려면 실제 수집·로그·저장 구조가 그 설명과 맞아야 한다. 필요 없는 식별 필드를 추가하지 않는다.

## Stitch 등 외부 시안 도구

시안 탐색·선택 영역 수정·화면 연결·규칙 내보내기의 역할로 검토한다. 학교 계정 허용 여부, 연령, 무료 한도, 공유·리믹스, 내보내기 기능은 작업 시 공식 문서와 실제 계정에서 확인한다. 학교 계정 제한을 우회하라고 안내하지 않는다.

도구 접속이나 계정이 막혀도 이어갈 수 있도록 승인된 시안·규칙·결정을 프로젝트에 남긴다. 외부 도구 연결이 없으면 그 기능을 사용했다고 주장하지 않고 로컬 밑그림 등 가능한 대안을 제안한다.
